# 巡检与停滞处理

2026-09-12 后续已由 [后台自愈服务](self-heal.md) 接管常规生产监测和按故障触发的修复。以下诊断与恢复要求继续有效，但不再依赖每 15 分钟唤醒模型执行。原定时任务改为仅在白天上传时间运行。

每次巡检先运行 `node scripts/patrol-health.mjs --check`。观察结果写入私有 `.runner/patrol-health.json`，包含实际运行数、待处理失败、连续空闲次数和最后完成时间。服务心跳正常不能代替生产进展；故障未变化仍是待处理事项，不能因为已上报就静默结案。

巡检可以在用户授权内修复本系统的编排、验收方法、补题和恢复逻辑，必要测试后按现有流程发布。若其他维护任务正在处理同一问题，记录负责人、处理动作、证据与下一检查点，避免并行修改或重复重试。转交、提交代码和排队都不是完成；要核对实际进入的阶段、新日志与后续结果。后台修复默认没有日次数或累计次数上限，失败后立即升级诊断，仍无法解决时立即通知；定时复核仅作兜底。既有业务恢复入口的安全重试规则保留，重复故障须先定位原因，不能无限点击重试。

午夜只暂停上传，生产和故障处理照常。正在执行的 Claude、原题、评分事实和原始轨迹不得为恢复而改写。独立验收失败时修复临时脚本，在冻结源码上重新运行；不得修改被测业务代码、删除原题验收或改变预期。

尚未发送的 Bug 草稿在原会话已经结束后，不能普通重发。只有容器结束回执、完整原生轨迹、前轮身份和源码归档均可核验时，才进入同项目独立续题流程。执行器重新核验原生末轮已经结束且属于已知前轮，复制验真的源码快照，保留未修复 Bug 和失败草稿，设计实质不同的 0-1 或 Feature 目标并独立审核。新题使用新容器和新会话，不改旧 Bug 分类，不增加原会话调用，不更换项目。项目 10+10 题额及真实发送计数仍按原规则。
