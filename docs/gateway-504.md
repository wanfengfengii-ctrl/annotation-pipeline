# 504 后在原会话发送继续

## 静默后的持续观察

2026-09-11 修复了网关重试比观察超时更长时的漏接：原生轨迹静默达到 `RUNNER_TIMEOUT_MS`（默认 30 分钟）后，执行器改为每 15 秒只读检查原会话，不再将本轮标为失败并退出观察。出现新的真实执行记录后恢复正常检查频率；迟到的成功进入原验收流程，迟到的 504 先按原始失败记录回写，再由现有规则安排继续。终端刷新不算实际进展，观察不会增加模型调用、重复发送题目或修改轨迹。

未知结束状态仍保留项目执行槽和原容器，不伪装为空闲；明确停止执行器、容器退出、身份异常、原件损坏仍会中止并保留证据。504 的完整结束、工具返回、权限核验和最多 10 次调用规则不变。此修复通过单题版本指针用于后续新领取任务，已加载旧版本的题目不热替换；历史已失败的观察记录仍需先核对真实结束状态再恢复。

用户于 2026-09-10 授权后续 504 自动发送继续。新版作业模块只在原生 API 错误事件明确包含 504、该轮已有完整结束标记、全部工具已返回且完整会话权限核验通过时产生版本化恢复证据。普通工具输出里的 504、502/503、页面接口超时、静默等待、权限错误均不触发。

API 在一次版本条件更新中保留失败轮并排入新轮，实际 Prompt 固定为“继续”，通过 continuationOf 关联紧邻失败轮，继承原任务的验收目标、准备记录与审核依据。原轮仍为 failed，原错误与原件保留；新轮有独立真实 PromptID 和实际轮次，不把继续写成 Bug，也不把两轮轨迹合并成一次成功。

发送前再次读取原 Terminal 的完整原生日志，核对失败事件摘要、原 PromptID/SessionID、容器及结束状态，仍走原有调用额度预占和发送回执。已发送但回写中断时仅观察原输入，不重发；重复 finish 不会重复创建继续。同会话最多十次实际调用，失败与继续都计数；最多初始题加两道 Bug 的业务题额不受继续消息影响，项目 0-1/Feature 各十题和 7:7:10:1:1 统计不重复累计恢复消息。

继续完成后，Codex 运行原目标的验收、评分及后续规划。504 轮没有业务验收报告时不伪造报告，原来已有的缺陷仍从已验证历史报告逐项继承复验。模型、网关、上下文和新独立题的容器规则不变。

用户进一步明确：继续只是完成上一道业务题，不单独计任务。记录列表、分页、筛选、勾选、Excel 和 SOLO 上传统一按原业务题归并；原题文字、原生 PromptID 和业务题起始的真实轮次取原题，评分、运行验收和内部交付包取最后继续完成的结果，附件取会话最终导出的完整原生轨迹。原题为 Bug 时只归并该 Bug 的继续，不归到会话最开始的项目生成题。数据库内原失败结果、继续的真实 ID、错误事件和调用次数原样保留；仅生成业务交付视图，不改写原件。

例如原生调用为第 1 轮原题 504、第 2 轮继续 504、第 3 轮继续成功、第 4 轮 Bug，则导出两条业务题，使用第 1、4 轮各自的原题及原生 ID；不把真实轮次压缩成 1、2。上传端从最终完整轨迹逐条验证原题及每个继续的身份、原文、实际轮次、前一轮已结束的 504 事件和评分目标，只有这些证明齐全时第 2、3 轮无需独立提交。后续 Bug 仍要求前一道业务题已有匹配当前结果的真实上传回执。

原题 ID 是稳定记录键，结果来源单独绑定继续轮。导出次数按整条链的不同导出批次累计，复核副本保留结果来源；保存的旧批次不会静默换用新评分或新轨迹。任何链成员被禁传、身份或验收目标错配、最终结果未完成、轨迹未收尾，均不能正式上传。旧继续轮已有独立远端记录或不明确提交时需核对，不自动再次合并上传。原题 504 不补造独立评分；归并题的评分描述完整完成过程。本地交付校验不代表外部平台已接受数据。

生效方式：先发布能接收新证据的本地 API，再切换后续 job 版本指针。已经加载旧模块的任务保持原版本，旧失败记录不会被扫描重放；后续新领取作业使用新逻辑。无需打断当前 Claude 或重启主 runner。
