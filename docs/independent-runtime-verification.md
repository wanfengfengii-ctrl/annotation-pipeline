# 独立运行验收

Claude 每次完成 0–1、Feature 或 Bug 修复后，评分前先执行以下步骤：

1. `runtime-plan`：Codex 只读检查原题、验收标准和实际源码，设计原题验收及疑似缺陷复现命令。
2. `runtime-running`：执行器复制代码到隔离工作区，使用原作业不可变镜像启动额外验收容器，每个业务检查使用单独的代码副本与容器，先执行共同 setup，再运行该项检查。保留脚本、退出码、日志、源码清单和摘要。
3. `runtime-diagnose`：Codex 读取原始输出、检查测试假设与原题范围，区分通过、已复现、未复现和环境阻塞。
4. 验收完成后，评分同时参考独立运行证据，但不得把验收工具调用算作 Claude 的行为。自动 Bug 题必须关联本轮已复现的检查 ID；有缺陷且仍有修复额度时先修复。修复后再次执行独立验收。

默认每轮执行预算 30 分钟、单步最多 10 分钟，最多 64 项；计划生成和诊断、评分不计入执行预算。每步计划时限是软期限，期间持续有新输出时可延长到配置上限；输出不等于断言通过。验收容器限制 2 核、3 GB、256 个进程，无宿主机端口、Docker socket、模型凭据或 Claude 会话挂载。原始产物和 native JSONL 不被修改。依赖、缓存、敏感配置与符号链接不复制；排除清单会交给验收规划器。

业务断言失败使用退出码 1，环境故障使用 2。超时、日志超限、源码被验收脚本修改或环境错误不能生成 Bug 题，轮次保留为可重试的验收阻塞。重试复用已经完成的 Claude 调用，不重新发送原题。未执行或不适用的检查不能算通过；静态怀疑未复现时不生成修复题。

运行报告、命令输出和 Codex 分析轨迹进入本轮证据归档并做 SHA-256 校验。前端展示具体检查、预期和实际结果及本机日志路径，导出字段保持既有表格约定。

已执行检查通过不代表穷尽所有 Bug。复现假设仍由模型判断，独立日志和原题要求保留供人工复核。浏览器交互需要适配项目依赖与浏览器运行环境，安装或运行失败会明确阻塞，不降级成假通过。

执行前检查 `2026-09-12.runtime-preflight4` 增加两类已出现的临时脚本检查：从预装 CommonJS Playwright 入口直接使用 ESM 命名导入，以及测试统计的首个 shell case 分支用空引号加星号匹配所有结果。命中后沿用现有的一次计划修订，保留原检查项目和预期；不执行或自动替换项目代码。语法通过仍不等于依赖可加载，环境准备须使用后续脚本相同的导入方式实际验证。

测试汇总区分有效的零次失败和缺失统计，保留套件原退出码与输出；包装脚本出错不能改称原测试失败。拖拽、排序等场景先观察实际页位变化，确认移动、交换或复制的真实行为后再断言提示和禁用状态；未形成目标场景不能仅凭等待预设选择器超时判为产品缺陷，也不能修改页面状态凑通过。

`2026-09-12.runtime-preflight5` 对只有总时限超限的计划使用专用预算修订：只生成各原步骤的 `id` 与 `timeoutSeconds`，执行器原样保留说明、顺序、命令、业务要求、预期及源码引用。增删步骤、重复 ID、附带其他字段或仍超限均拒绝；完整计划、原始补丁和预检结果保留。其他错误仍走既有完整计划修订及严格一致性检查，不因文字意思相近放行改写。服务从隔离副本显式指定工作目录启动，健康检查失败先保留实际启动日志和退出码，不能丢掉错误输出后误判产品。

浏览器唯一定位辅助函数对页面重绘保留一个总计5秒的等待期限。元素出现后、计数前短暂消失时，记录一次重试原因并重新解析同一定位器；多个匹配立即拒绝，持续缺失或超时仍为验收阻塞。返回值始终是原定位器，不用第一项代替唯一性，不修改页面，也不把字段出现等同业务检查通过。旧失败报告与原始轨迹保留，补验须另行实际执行。

项目用例库保存到 `.runner/<task>/verification-suite/`，脚本与来源清单不可覆盖。已有项目从最近一份验真的完整报告建立基线；后续 Feature 只输出新增用例和实际需要修改的脚本，旧脚本由系统原样带入。Bug 修复可直接重跑选中的原复现用例。每个新题均实际执行合并后的计划，不沿用上一题的通过结果。旧业务的检查按其原题要求诊断，未被本题选中的历史问题不算本题评分义务。

同题恢复保存计划检查点与 `.runner/<task>/runtime-progress/` 逐项执行凭据；任务 ID、逻辑题 ID、代码清单、输入、镜像、辅助工具及命令一致且日志摘要正确，才恢复已完成步骤的执行证据。每个业务用例在独立环境运行，不能依赖前一业务用例留下的文件或服务；共享脚本、依赖和服务放在 setup。失败用例重新准备自己的隔离环境，已完成业务用例不重跑。修改 setup 会使相关业务缓存失效。代码或题目变化重新验收，历史未保存逐项凭据的执行不能追认断点。

超时或脚本问题保留计划、原日志、源码副本和实际执行结果，不把整个 Claude 任务直接判失败。单步超时先进行一次有界重试，仍未完成则排队续跑，API 显示验收待续跑；相同代码的脚本问题只修订阻塞步骤。连续三次恢复未完成任何新业务检查时显示验收待处理，可用重新验收继续；原始 Claude 调用和轨迹保留，不新建题目或追加 Claude 调用。实际业务断言失败仍记录为已复现缺陷，不能因有输出而算通过。

在工作根目录 `.runner/runtime-verification-settings.json` 配置执行预算，例如：

```json
{"totalTimeoutSeconds":1800,"stepTimeoutSeconds":600,"maxChecks":64}
```

总预算可设 60–7200 秒，单步为 1–1800 秒且不大于总预算，用例最多 64 项。配置在下一次验收读取，正在执行的命令保持启动时预算。预算耗尽后剩余用例进入下一次恢复，不因预算不足跳过检查。完成报告也可跨已校验的冻结执行器版本复用，但仍须核对同题输入、当前源码与全部原始证据。
