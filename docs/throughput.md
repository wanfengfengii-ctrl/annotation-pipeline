# 本机流水线效率改进

本次目标是减少环境准备、排队、归档和重复后处理的时间。产物有业务缺陷不自动等于标注无效，仍保留原题、实际结果、评分和原始轨迹。实际收益在上线后按 24 小时样本比较，不预报固定日产量。

## 调度与收尾

最多三个项目同时执行。Claude 执行、Codex 准备与评分、重型验收共享一个总预算；Codex 同时一个，重型验收同时一个，优先评分、交付和后续规划。新建项目容器前在基础保留内存之外预留至少 768 MiB 验收空间；单次验收按实际预算分配 768 MiB–2 GiB，宿主负载、Docker 余量和内存压力继续限制准入。已存在的作业容器内进行环境准备，不重复申请新验收容器的内存，但仍占用共享执行额度和单个重型阶段额度。降低并发只影响新阶段，不终止正在执行的模型。

独立归档队列在当前原题已完成且下一步为新题、结束或暂停时启动，不等待下一题领取。队列先占任务锁，发送退出前再次比对 API 决策及原生末轮，原 Mac Terminal 执行最终导出与清理；原件逐字节核验和最终回执沿用原流程。排队中的同会话 Bug、活动阶段、未确认输入及旧终端协议不自动收尾。失败仍保留失败状态和证据；只有原生完成证据满足条件时释放容器，不重发错误或不明状态的题目。

模型原生进展停滞 10 分钟标记观察，20 分钟标记终端复核；工具开始、结果和最后进展记录为旁路元数据，不修改轨迹。多个项目短期出现真实接口错误时暂停新会话五分钟，之后一次只放入一个真实新任务，以其调用结果判断恢复。业务质量失败不计为网关故障。

接口错误发生前已有工具调用时，只有所有工具都收到对应返回、原生末轮已写完成标记且没有新输入，才允许在原 Terminal 结束失败会话。失败记录和原始轨迹保留。旧协议不能自动取得新导出能力；经同样核对后只在原终端退出并停止容器，完整容器保留在磁盘，等待原终端归档，不伪造最终导出或上传准入。已确认停止的容器不占运行内存额度，身份未知仍保留额度。

## 环境与候选

新作业镜像为 annotation-pipeline/claude-code:2.1.266-webdeps-20260910，保留原入口、node 用户、Claude 2.1.266、既有模型与网关及 1,000,000 上下文。预装 pip、venv、常用 Python Web/测试依赖、ffmpeg、Python 与 Node Playwright 1.62.0 和 Chromium 系统库。Python 完整版本锁与依赖摘要随镜像保存，实际任务绑定不可变镜像 ID。旧会话和旧快照继续使用原镜像。

提供 Flask、Node HTTP 两种仅含入口和空页面的通用骨架，Codex 可按业务适配或选择其他技术栈。每次独立题发送前，在实际新容器验证导入、创建带 pip 的虚拟环境、浏览器真实点击；新项目还要通过 Codex 给出的网页启动与通用冒烟命令。按依赖清单准备环境并验证原源码没有变化，失败保留日志，不发送题目。依赖安装不包含历史对话、代理记忆或业务答案；它不会强制业务布局。

开题前以原 node 用户配置并校验可写 npm 缓存，避免镜像构建遗留的 root 所有权导致 npm 安装失败；不改变作业容器权限、模型配置或源码。当前项目已通过实际依赖安装、浏览器和虚拟环境检查，准备失败的未发送题目可在修复环境后继续，旧失败日志仍保留。

候选缓冲最多两条，数据库原子校验上限、每日额度与重复指纹。入队前完成题面、禁出、难度审核；真正发送前结合冻结代码再次审查。后续功能和 Bug 根据真实上一轮结果生成，不提前编造。每题聚焦一个完整业务流程，原有字数、关联操作、细节、禁题、难度、去重、7:7:10:1:1 和 Bug 轮数上限全部保留。

## 后处理与发布

原题、源码摘要、真实运行记录及原件引用形成冻结事实索引，供评分与交付复核回查。阶段缓存按该阶段的规则、输入及证据摘要验证，运行验收另绑定执行实现与镜像。源码哈希缓存只在单次尝试内使用，仍枚举所有文件并检查 inode、大小、mtime 和 ctime；实际归档继续重新读取和核验原件。

执行器与单题执行模块已拆开。scripts/publish-job-release.mjs 将已验证提交冻结到本机 releases，校验完整代码清单后原子更新下一题版本指针。当前题继续使用已加载的不可变模块，后续领取加载新版本，共用同一个所有者、任务锁和资源预算。首次采用这套机制以及不兼容的终端/API 协议更新仍需自然收尾切换，不能同时启动两个主执行器。

此机制适用于兼容的单题代码更新。npm 依赖升级、主调度器和容器协议变化仍按 Mac 安装文档等待现有作业收尾再更新；不能在作业运行时替换共用 node_modules。版本指针、计时、首条链验证状态和本机回执不通过 Git 复制到其他电脑。

用户已要求直接最多三个项目并行，当前使用 user-expanded 状态，取消首条链验证等待，不标记为验证通过。单项目验证功能仅保留为可选机制；后续巡检不得擅自重新开启。逐题质量、权限、原始轨迹和上传检查继续执行，发现实际问题后处理。

## 观测与验证

每次尝试写独立追加计时日志，记录排队、各阶段起止和结果，重试不覆盖前次时间。页面分别显示已评分、已最终归档、已上传、质检通过和待返修数量，以及按题型、难度分组的尝试耗时。旧记录缺少计时就标为缺失，不用负时长或伪造时间补齐。

scripts/throughput-report.mjs 保存本机基线与最新统计，24 小时后比较新增通过量和同题型耗时。正常条件下的目标是满足收尾条件后五分钟内归档、资源足够且有合格题时一分钟内补位；20% 耗时下降是待验证目标。累计历史数量不能当作稳定日产率。

验证包括独立测试数据库的原子领取/补题、三个模拟项目并行、评分中断后仅重试失败阶段、完整项目会话链、原终端收尾与原生附件测试；两种通用骨架还在真实派生镜像中启动网页并通过浏览器和冒烟检查。生产模型原会话不参与这些模拟测试。

Python 虚拟环境和浏览器准备方式参考 [Python venv](https://docs.python.org/3/library/venv.html) 与 [Playwright Docker 文档](https://playwright.dev/python/docs/docker)。
