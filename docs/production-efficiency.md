# 生产重复处理修复

2026-09-12：保留三项目并行、原 Mac Terminal 执行、原生轨迹及现有质量判断。

- 验收计划增量草稿修订为完整计划时，沿用已验真的用例库来源，原有检查不能丢失。现有 `cc584f0` 已处理这一问题，本轮继续跑对应回归；同题、源码、命令和证据摘要一致的已完成检查仍由现有检查点复用。
- 自愈诊断使用容器 pending 中的题面摘要，在本轮准备记录中找到实际发送内容，再精确匹配原生消息。不再用可能尚未更新的 API 草稿匹配。没有对应准备记录时如实报告证据缺失，空白近似匹配只用于诊断，不授权重新发送或宣布完成。
- 评分先核对事实、引用及分数描述冲突，再处理口语化表达。沿用冻结事实索引和真实验收覆盖，不增加首次评分调用，不重新运行验收。表达修订保留分数与内部事实；`.consistency.clarity.score` 的复评结果可按原摘要校验继续用于交付返修，原始点评和轨迹不改写。评分校验及修订代码加入检查点契约摘要，避免继续采用旧规则的缓存。
- 项目重出题在生成候选之前就因环境、源码或会话条件失败时，记录当时的条件摘要。API 心跳、累计次数和等待时长不能使同一失败重复启动；容器/归档等实际条件变化或发布修复版本后，按原有有限次数恢复。已生成但不合规的候选仍走原有审核与重出逻辑。
- 归档先复核计划对应的实际容器和题目，完成回调成功后才在队列标记完成。失败记录持久化到 `.runner/finalization-queue.json`，普通失败等待条件或归档代码变化；明确的网络错误最多在相同条件下补试一次。其他项目可继续归档。后台自愈会读取这些失败，不再只把错误打印在日志里。
- 自动修复遇到同一故障、同一证据与同一代码条件时，保留诊断和复核意见，进入 `waiting_conditions`，不立即再花一次模型调用尝试相同补丁。条件变化后沿用原有次数和预算；新诊断可读取最近同类诊断及复核。模型修复日预算用完不妨碍原有的一次受保护网络恢复操作。

以上等待仅针对已经失败且前提未变的动作，不按总时长打断有进展的作业，不把等待或新题启动当成旧归档完成。发布只切换后续认领作业，活跃任务使用原冻结版本；主执行器及其归档队列在空闲交接后采用新代码。
